# Insurance Claims RAG — Application Summary

## Overview

A full-stack **Retrieval-Augmented Generation (RAG)** application for insurance claims document Q&A.

Users upload insurance documents through an Angular UI. Files are stored in **Azurite** (Azure Blob API), metadata and chat history live in **SQL Server**, embeddings are indexed in **ChromaDB**, and answers are generated by a local **Ollama** LLM — with source citations shown in the chat UI.

> There is **no Streamlit** UI. The only application frontend is Angular.

---

## Architecture

```text
Angular (UI :4200)
        │ HTTP
        ▼
FastAPI (API :8000)
   ├── SQL Server     → metadata, conversations, messages, RAG sources
   ├── Azurite        → actual PDF/DOCX/TXT binaries
   ├── ChromaDB       → vector embeddings
   └── Ollama         → local LLM answers
```

## What the Application Does

### 1. Document management
- Upload PDF, DOCX, or TXT (drag & drop or browse)
- Validate type and size
- Store the binary in Azurite blob container `insurance-documents`
- Store metadata in SQL Server (`Documents` table)
- Process asynchronously in the background:
  - Extract text
  - Chunk text
  - Generate embeddings
  - Index in ChromaDB
  - Persist chunk metadata in SQL (`DocumentChunks`)
- Track status: `Uploaded` → `Processing` → `Processed` / `Failed`
- List, search, filter, reprocess, download, delete documents
- View document details (pages, chunks, blob metadata, errors)

### 2. Conversational RAG chat
- Create / rename / delete conversations
- Ask questions about uploaded claim documents
- Retrieve top-K relevant chunks from ChromaDB
- Generate grounded answers via Ollama
- Show source citations (document name, page, relevance score)
- Persist conversations, messages, and RAG sources in SQL Server
- Support regenerate answer, copy answer, clear conversation

### 3. Dashboard
- Totals for documents (all / processed / processing / failed)
- Conversation and question counts
- Recent documents and conversations

## Database Schema (SQL Server: `InsuranceRagDb`)

| Table | Stores |
|---|---|
| `Documents` | File metadata, blob path, hash, status, timestamps |
| `DocumentChunks` | Chunk text metadata (not embedding vectors) |
| `Conversations` | Chat sessions |
| `Messages` | User / assistant / system messages |
| `RAGSources` | Citation links from assistant messages to docs/chunks |

Migrations are managed with **Alembic** and run automatically on backend startup.

## RAG Pipeline

```text
User question
  → embed query
  → ChromaDB similarity search (TOP_K, SIMILARITY_THRESHOLD)
  → build context from retrieved chunks
  → prompt Ollama (answer only from context; cite docs/pages)
  → return answer + sources
  → persist message + RAGSources in SQL Server
```

Default RAG settings (configurable via `.env`):
- `CHUNK_SIZE=800`
- `CHUNK_OVERLAP=150`
- `TOP_K=5`
- `SIMILARITY_THRESHOLD=0.3`
- `EMBEDDING_MODEL=all-MiniLM-L6-v2`
- `OLLAMA_MODEL=llama3.2`

## Security / Design Notes (POC)

- No auth required for local POC (architecture ready to add later)
- Angular talks only to FastAPI (no direct DB/blob credentials in the browser)
- Upload validation (extension, MIME where possible, max size)
- Filename sanitization; server-generated blob names
- Configurable CORS origins (not `*`)
- Structured backend logging
- Consistent JSON error responses

## End-to-End Happy Path

1. Open http://localhost:4200 → **Documents**
2. Upload `sample-data/claim-investigation-report.pdf`
3. Wait until status is **Processed**
4. Open **Chat**
5. Ask: *What was the cause of the loss?*
6. Get answer + source citations (document + page)
7. Restart Docker — conversation remains in SQL Server

## Azure Migration Path

Designed so local infra can be swapped later without a major rewrite:

| Local | Azure |
|---|---|
| Azurite | Azure Blob Storage |
| SQL Server Docker | Azure SQL |
| ChromaDB | Azure AI Search / managed vector DB |
| Ollama | Azure OpenAI / hosted LLM |

Service abstractions (`BlobService`, `VectorStoreService`, `LLMService`, `EmbeddingService`) keep that migration localized.
