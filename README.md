# Insurance Claims RAG

Full-stack **Retrieval-Augmented Generation** application for insurance claim documents.

Users upload claim PDFs/DOCX/TXT through an **Angular** UI. Files are stored in **Azurite** (Azure Blob API), metadata and conversations live in **SQL Server**, embeddings are indexed in **ChromaDB**, and answers are generated by a local **Ollama** LLM.

> This project does **not** use Streamlit. The only application UI is Angular.

---

## Architecture

```text
Angular (UI)
   │ HTTP
   ▼
FastAPI
   ├── SQL Server      (metadata, conversations, messages, RAG sources)
   ├── Azurite         (actual document binaries)
   ├── ChromaDB        (vector embeddings)
   └── Ollama          (local LLM)
```

## Quick Start

1. Copy environment file:

```bash
cp .env.example .env
```

On Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

2. Start the stack:

```bash
docker compose up --build
```

First startup can take several minutes while:

- SQL Server initializes
- Backend installs/loads the embedding model
- Ollama pulls `llama3.2`

3. Open the app:

| Service | URL |
|---|---|
| Angular UI | http://localhost:4200 |
| FastAPI / Swagger | http://localhost:8000/docs |
| Health | http://localhost:8000/api/health |
| ChromaDB | http://localhost:8001 |
| Azurite Blob | http://localhost:10000 |
| Ollama | http://localhost:11434 |

## SQL Server / SSMS

SQL Server runs **inside Docker**. SSMS remains on your Windows host.

| Setting | Value |
|---|---|
| Server | `localhost,1433` |
| Authentication | SQL Server Authentication |
| Login | `sa` |
| Password | value of `SQL_SERVER_PASSWORD` in `.env` |
| Database | `InsuranceRagDb` |

Do **not** install SSMS in the container.

---

## Azurite (Blob Storage)

Uploaded documents are stored in the Azurite container:

```text
insurance-documents
```

SQL Server stores only metadata (name, hash, blob path, status, etc.). Document binaries are **not** kept in the backend filesystem permanently.

Data persists in the Docker volume `azurite_data`.

---

## ChromaDB

Collection:

```text
insurance_claims_documents
```

Persisted in Docker volume `chromadb_data`.

Each vector includes metadata such as `document_id`, `file_name`, `page_number`, `chunk_id`, and `chunk_index`.

---

## Ollama

Configured via:

```env
OLLAMA_BASE_URL=http://ollama:11434
OLLAMA_MODEL=llama3.2
```

The `ollama-init` service pulls the configured model on startup.

To pull manually:

```bash
docker compose exec ollama ollama pull llama3.2
```

## End-to-End Demo Flow

1. Open http://localhost:4200
2. Go to **Documents**
3. Upload `sample-data/claim-investigation-report.pdf`
4. Wait until status becomes **Processed**
5. Open **Chat**
6. Ask: `What was the cause of the loss?`
7. Review answer + source citations (document + page)
8. Restart containers and confirm the conversation still exists

All important settings are environment-driven. See `.env.example`.

## Azure Migration Path

The architecture is intentionally swappable:

| Local | Azure |
|---|---|
| Azurite | Azure Blob Storage |
| SQL Server Docker | Azure SQL |
| ChromaDB | Azure AI Search / managed vector DB |
| Ollama | Azure OpenAI / hosted LLM |

Service interfaces (`BlobService`, `VectorStoreService`, `LLMService`, `EmbeddingService`) keep that migration localized.

## Troubleshooting

- **Backend unhealthy / SQL errors:** wait for SQL Server healthcheck; confirm `SQL_SERVER_PASSWORD` meets complexity rules.
- **Chat answers empty / slow:** confirm `ollama-init` finished pulling the model (`docker compose logs ollama-init`).
- **Upload fails:** verify Azurite is up on port `10000`.
- **No sources returned:** ensure at least one document is in `Processed` status and adjust `SIMILARITY_THRESHOLD` if needed.
